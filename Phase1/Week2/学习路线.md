# 第 2 周：音视频开发环境自检

## 本周概览

### 所属阶段

根路线阶段 0“基线与环境”（第 1-2 周），目录映射为 `Phase1/Week2`。第 1 周已通过双编译器、CMake、CTest、Git 与 GDB 基线；其 `baseline` 最终判断占位和未提交改动是非阻塞欠账，本周不修改 `Week1`。本周建立 FFmpeg、SDL2/OpenGL、Wireshark 与 Sanitizer 的可重复环境证据，为第 3 周的 C++/Linux 工程练习和第 13 周后的媒体实验提供统一入口。

### 这周学什么

- **工具与开发库发现**：区分 CLI、运行库、头文件和链接库；会用 `command -v`、`--version`、`pkg-config` 与 CMake package discovery 判断“已安装”和“可开发”是否成立。
- **FFmpeg 工具链与合法素材**：会用 `ffmpeg` 的 `lavfi` 自生成短音视频，并用 `ffprobe` 核对容器、流类型、尺寸、采样率和时长；不进入解复用或解码 API。
- **SDL2/OpenGL 最小上下文**：优先 SDL2，仅验证窗口/上下文创建、版本与 OpenGL 信息读取及反向清理；Qt 只做已安装则记录的 P1。
- **调试与动态检查**：用 GDB batch 模式验证符号和断点；分别验证 ASan、UBSan 可编译、可运行且能识别受控故障。
- **网络诊断工具边界**：检测 Wireshark GUI 命令和版本；用 `tshark`/`dumpcap` 查询接口与权限，不要求、也不保存真实敏感抓包。

### 本周项目

实现可重复的 `av-env-check`：按固定顺序执行命令/版本检查、开发库发现、FFmpeg 与 SDL2/OpenGL 两个 smoke tests、GDB 与 Sanitizer 探针、合法测试素材及 `ffprobe` 元数据检查，最后生成文本报告并返回确定退出码。编写 `project/av-env-check.sh` 作为主入口，调用 C++ smoke 程序。P0 链路为“本机环境 -> 独立检查项 -> PASS/FAIL/SKIP 汇总 -> 报告与退出码”；本周只做当前项目需要的顺序脚本，不抽象通用命令执行框架。

### 完成标准

- README 中的 configure、build、test、check 四步可从空 build 目录复现；检查报告顺序稳定，必需检查全过返回 `0`，任一必需检查失败返回约定非零码。
- FFmpeg、SDL2 和 OpenGL 开发能力均经过 configure 与 compile/link 验证；FFmpeg 必须完成 runtime，SDL2/OpenGL 在有图形会话时完成 runtime，纯 headless 时明确 `SKIP` 并列入第 17 周前重验。
- GDB batch 检查能命中符号；ASan/UBSan 分别有 clean case 和受控 fault case，诊断与预期退出行为可复核。
- 自生成素材来源、生成命令和 `ffprobe` 元数据明确；不下载版权不明素材。
- 至少 6 个自动测试覆盖 3 个正常/边界场景和 3 个错误/降级场景，并确认临时文件、窗口和 GL context 均被清理。

### 最终交付物

- `project/`：`av-env-check` 的 CMake、主入口脚本、最小 smoke 源码、测试和准确 README。
- `project/assets/README.md` 与自生成的小型测试素材：记录来源、生成命令和预期元数据。
- `evidence/tool-versions.txt`：工具、编译器、开发库发现结果的真实版本或缺失状态。
- `evidence/env-report.txt`：一次最终 P0 自检报告、汇总和入口命令退出码。
- `evidence/ffprobe.json`：自生成素材的真实探测结果。
- `evidence/ctest.log`、`evidence/sanitizers.log`、`evidence/gdb-session.txt`：自动测试、Sanitizer 与 GDB 证据。
- `notes/environment.md`：安装方式、CLI/开发包区别、权限/图形会话限制及未解决项。

### 本周不做

不编写解码器、播放器、采集或网络协议；不调用 FFmpeg 解码 API；不同时实现 SDL2 与 Qt 两条 GUI 线；不下载版权不明素材；不抓取或保存真实敏感流量；不修改第 1 周文件；不把尚未执行的构建/运行命令描述为已可用。

## 每日任务

### 第 1 天：环境盘点与检查契约（预计 3.25 小时）

#### 今日目标

得到真实的工具/开发库缺口清单，并冻结 `av-env-check` 的检查项、状态和退出码契约。

#### 学什么

- **必须掌握**：可执行程序、运行库、开发包（headers/link libraries）的区别；“命令存在”不等于“程序可编译”。
- **必须会用**：`command -v`、各工具的官方 `--version`/`-version`、`pkg-config --modversion`/`--exists`、CMake configure 输出和 `$?`。
- **了解即可**：发行版包名差异；只在笔记记录当前机器实际安装方式。

#### 怎么学

先复跑 Week1 README 中双编译器的预期干净构建流程，只判断是否漂移，不改 Week1。再按 CLI（`ffmpeg`、`ffprobe`、`gdb`、`wireshark`、`tshark`、`dumpcap`）和开发库（FFmpeg 各库、SDL2、OpenGL）分组查询官方帮助、`pkg-config` 元数据与 CMake discovery。每次同时记录完整命令、stdout/stderr 和退出码；缺失时查当前发行版官方包信息并安装，安装失败保留原始错误。

#### 动手任务

- 列出 check ID、前置依赖、PASS/FAIL/SKIP 条件和是否阻塞；固定退出码：`0` 为全部必需检查通过（允许有文档明确许可的环境型 `SKIP`），`1` 为至少一个必需检查失败，`2` 为入口参数或报告生成错误。
- 规划稳定报告字段：check ID、status、summary、detail/evidence；不得依据本机当前状态硬编码 PASS。
- 检测 Wireshark GUI 是否存在；仅运行版本查询。运行 `tshark -D` 或 `dumpcap -D` 只验证列举接口的能力，不开始 capture；权限不足按真实结果记录。

#### 当天交付

- `project/README.md`：写入项目边界、P0/P1/不做、状态/退出码契约和预期命令。
- `evidence/tool-versions.txt`：写入日期、系统、GCC/Clang/CMake、FFmpeg/ffprobe、SDL2/OpenGL discovery、GDB、Wireshark/tshark/dumpcap、ASan/UBSan 的真实结果或 `MISSING/NOT_CHECKED`。
- `notes/environment.md`：写入当前发行版安装来源、CLI 与开发包对应关系、图形会话和抓包权限限制、阻塞清单。

#### 自测问题

1. 为什么 `ffmpeg -version` 成功仍不能证明 `libavformat` 开发头文件可用？
2. `pkg-config --exists` 与真正 compile/link smoke test 分别能证明什么？
3. 缺少 `dumpcap` 权限应是环境信息、P0 失败还是敏感抓包任务？如何由契约决定？

#### 结束条件

- [ ] 所有目标工具均有真实版本、缺失或未检查状态，没有空白和猜测值。
- [ ] 每个 P0 check 都有唯一 ID、判断条件和证据来源，三类退出码无歧义。
- [ ] Week1 基线漂移有结论；其欠账未被本周文件改动。

### 第 2 天：CMake 发现与项目骨架（预计 3.25 小时）

#### 今日目标

让 CMake 在干净 build 目录中明确发现或拒绝 FFmpeg、SDL2 与 OpenGL，并建立可测试的自检骨架。

#### 学什么

- **必须掌握**：configure-time discovery 与 compile/link/runtime 验证的边界；required 与 optional dependency 的差别。
- **必须会用**：imported target、`find_package(OpenGL)`、SDL2 的 CMake config 或 `pkg-config` fallback、FFmpeg 的 `pkg-config` modules、CTest 注册。
- **了解即可**：Qt discovery；本周只在已安装时记录为 P1，不建立第二套 smoke 源码。

#### 怎么学

先查看当前安装包提供的 CMake config 和 `.pc` 文件，再为每个依赖选择当前系统真实可用的一条发现路径，避免猜库名。用空 build 目录观察 configure；缺少依赖时保留真实失败并确认错误指向具体库。只搭建本周两个 smoke targets 和测试入口，不设计通用检查类层次。

#### 动手任务

- 创建顶层 CMake 骨架，定义 `ffmpeg_smoke`、`sdl_gl_smoke` 和后续 Sanitizer 探针 targets；缺失必需依赖时给出明确 configure 错误。
- 创建 `src/`、`tests/` 最小骨架和脚本入口；未实现检查必须输出 `NOT_CHECKED` 并返回非零，不得伪造 PASS。
- 注册 smoke 正常运行测试占位；不得将本机绝对路径写入源码。

#### 当天交付

- `project/CMakeLists.txt`：C++17、依赖发现、targets、警告与 CTest 骨架。
- `project/av-env-check.sh`、`project/tests/CMakeLists.txt`：bash 入口脚本与 CMake 测试注册骨架，未实现路径明确返回“未实现”而非假 PASS。
- `evidence/configure.log`：一次成功或真实失败的干净 configure 命令、输出和退出码。

#### 自测问题

1. `pkg-config` 返回版本后，为什么还需要 link 与 runtime smoke test？
2. CMake imported target 相比手写 `-I/-L/-l` 减少了哪些环境假设？
3. optional Qt 缺失为何不能改变 SDL2 P0 的结果？

#### 结束条件

- [ ] 从空 build 目录 configure，不会静默忽略任何 P0 开发库。
- [ ] 若当前确有依赖缺失，configure 错误包含 dependency 名称且退出非零；依赖齐全时不为此破坏系统环境。
- [ ] 骨架未硬编码本机绝对路径，也未把 TODO 输出为 PASS。

### 第 3 天：FFmpeg、SDL2 与 OpenGL smoke tests（预计 3.25 小时）

#### 今日目标

完成三个最小 compile/link/runtime 探针，并在成功和初始化失败时都正确释放资源。

#### 学什么

- **必须会用**：FFmpeg 库版本查询 API；SDL 初始化、窗口创建、OpenGL context 创建与 `glGetString`。
- **必须掌握**：反向释放顺序、部分初始化失败时只释放已取得资源、stderr 与退出码契约。
- **了解即可**：OpenGL profile/version 差异；本周不写 shader、不渲染媒体。

#### 怎么学

按 FFmpeg 官方 headers/Doxygen 核对版本 API；按 SDL2 官方文档和 Khronos 文档核对 context 生命周期。先分别编译运行最小探针，观察链接库与运行输出；再仅对测试命令移除图形会话变量，确认 SDL/OpenGL 失败可行动且没有伪造 GL 信息。通过返回路径和日志确认 cleanup；不扩展为播放器窗口。

#### 动手任务

- `ffmpeg_smoke` 输出编译期/运行期可识别的库版本并返回确定状态，不打开媒体、不解码。
- `sdl_gl_smoke` 创建最小隐藏窗口与 GL context，读取 SDL/OpenGL vendor/version 后按 context -> window -> SDL 的反向顺序清理。
- 注入无图形会话、SDL init 失败或 context 创建失败；确认已获得资源仍被释放，错误写 stderr。

#### 当天交付

- `project/src/ffmpeg_smoke.cpp`：最小版本/link/runtime 探针。
- `project/src/sdl_gl_smoke.cpp`：SDL2/OpenGL 最小上下文探针及失败清理实现。
- `project/CMakeLists.txt`、`project/tests/CMakeLists.txt`：接入两个 smoke targets 与正常/无图形会话测试。
- `evidence/smoke-tests.log`：记录预期命令的实际执行输出、退出码及图形环境说明。

#### 自测问题

1. FFmpeg CLI 版本和 linked library 版本为何可能不同？
2. SDL window 已创建但 GL context 创建失败时，应按什么顺序清理？
3. headless 运行失败如何与“OpenGL 开发库未安装”区分？

#### 结束条件

- [ ] FFmpeg 与 SDL2/OpenGL targets 均完成 compile/link，runtime 输出来自真实 API。
- [ ] FFmpeg runtime 返回 `0`；有图形会话时 SDL2/OpenGL runtime 返回 `0`，纯 headless 时按契约明确 `SKIP` 并列入重验项，不写 PASS。
- [ ] 至少一个部分初始化失败路径被执行，窗口/context/SDL 状态均完成清理。

### 第 4 天：素材、ffprobe 与自检主链路（预计 3.5 小时）

#### 今日目标

用合法自生成素材打通“生成 -> 探测 -> 检查 -> 汇总报告 -> 退出码”P0 主链路。

#### 学什么

- **必须会用**：FFmpeg `lavfi` 的 `testsrc`/`sine` 输入、显式时长与输出覆盖选项；`ffprobe` JSON 输出和 stream/format 字段选择。
- **必须掌握**：容器、video/audio stream 与元数据检查的边界；子进程退出码和报告状态必须一致。
- **了解即可**：编码参数含义；只选当前环境可用的标准编码器生成极短素材。

#### 怎么学

先查 `ffmpeg -filters`、`ffmpeg -encoders` 和 ffprobe 官方选项，依据本机实际能力选择可复现命令，不假定特定可选编码器存在。生成 2-3 秒测试图与正弦音频，使用 ffprobe 只输出需要字段，人工核对流数、类型、尺寸、采样率和时长容差。随后将每个探针接入聚合器，故意传入不存在命令和损坏素材观察报告及最终退出码。

#### 动手任务

- 创建一份仓库内自生成小素材；README 记录生成命令、生成日期、来源=`lavfi`、预期字段和许可说明。
- 在 bash 脚本中实现固定顺序检查、临时目录清理、文本报告和退出码映射；直接处理命令缺失与非零，不扩展通用 timeout/进程管理框架。
- 对损坏或非媒体文件运行 ffprobe 检查，确认不会沿用上一次成功元数据。

#### 当天交付

- `project/assets/README.md` 与 `project/assets/generated-smoke.<实际扩展名>`：自生成素材、命令和元数据约定。
- `project/av-env-check.sh`：bash 编写的 P0 主链路、报告和退出码实现。
- `evidence/ffprobe.json`：对仓库内自生成素材的真实探测结果。
- `evidence/env-report-draft.txt`：首次全链路报告，允许含真实 FAIL，但不得含假 PASS。

#### 自测问题

1. 为什么仅看文件扩展名不能证明素材的容器与流类型？
2. 外部命令不存在、命令返回非零和报告写入失败应如何区分？
3. 如何证明测试素材合法且别人能复现？

#### 结束条件

- [ ] 素材完全由记录的 `lavfi` 命令生成，无外部下载来源。
- [ ] ffprobe 证据至少包含 video/audio stream 类型及约定的尺寸、采样率、时长字段，数值在文档容差内。
- [ ] 正常主链路返回 `0`；至少两个故障注入返回约定非零，报告无陈旧成功值，临时目录被清理。

### 第 5 天：GDB、Sanitizer 与故障回归（预计 3.25 小时）

#### 今日目标

证明调试器和两类 Sanitizer 实际生效，并把正常、边界、错误及清理行为纳入自动回归。

#### 学什么

- **必须会用**：GDB `--batch`、break/run/bt；`-fsanitize=address`、`-fsanitize=undefined` 及对应运行诊断。
- **必须掌握**：sanitizer clean run 与故障探针各自证明的内容；预期故障测试必须验证非零退出与诊断特征。
- **了解即可**：LeakSanitizer 平台差异；本周不引入 TSan、Valgrind 或性能分析。

#### 怎么学

使用 Debug target 让 GDB batch 在已知函数处命中并输出 backtrace。为 ASan 和 UBSan 各保留一个小型、隔离、只用于测试的受控 fault target，先运行 clean case，再运行 fault case；诊断文本和退出状态同时核对，避免“程序崩了所以 sanitizer 可用”的错误结论。最后用 CTest 覆盖正常 smoke、坏素材、无图形会话和必需命令缺失模拟。

#### 动手任务

- 添加 ASan/UBSan clean 与 fault targets；fault target 不被正常入口调用，也不提交 core dump 或大型转储。
- 建立至少 6 个自动测试：至少 3 个正常/边界、3 个失败/降级，包含报告退出码、坏素材、必需命令缺失模拟和无图形会话。
- 使用 GDB batch 验证符号、断点和调用栈；测试结束检查无遗留窗口或临时目录。

#### 当天交付

- `project/tests/`：Sanitizer 探针、fixture/runner 与至少 6 个 CTest 场景。
- `project/CMakeLists.txt`、`project/tests/CMakeLists.txt`：独立 Sanitizer targets 与测试属性。
- `evidence/sanitizers.log`：ASan/UBSan clean 和 fault 的命令、关键诊断与退出码。
- `evidence/gdb-session.txt`：batch 命中断点、符号、调用栈及退出结果。
- `evidence/ctest.log`：测试总数、分类、全部通过结果和退出码。

#### 自测问题

1. 为什么只有 sanitizer clean run 不能证明错误检测链路有效？
2. 如何让“预期崩溃”测试通过，同时避免吞掉错误？
3. GDB 能启动程序但断点没有源码位置时，应先检查什么？
4. 如何验证失败路径没有遗留资源或进程？

#### 结束条件

- [ ] GDB batch 命中项目函数并输出可识别调用路径。
- [ ] ASan、UBSan 各有 clean case 通过、fault case 被识别，日志中工具与退出行为匹配。
- [ ] 至少 6 个测试全部通过，3 类失败/降级场景均有断言，测试后无遗留资源。

### 第 6 天：干净复现与文档收口（预计 3 小时，含 1 小时缓冲）

#### 今日目标

只依照 README 从干净 build 目录复现 P0，形成可供后续周复用的最终报告；用明确缓冲修复遗漏，不增加新功能。

#### 学什么

- **必须掌握**：环境可复现证据必须同时包含版本、发现、编译、运行、失败行为和限制。
- **必须会用**：按“工具存在 -> CMake discovery -> compile/link -> runtime -> report/test”顺序定位复现失败。

#### 怎么学

## 常见风险与降级方案

- **安装或下载超过 2 小时**：停止反复换源，保留包管理器错误；优先保证 FFmpeg CLI+dev、SDL2/OpenGL dev、GDB 和 Sanitizer P0，Qt 永久降为 P1。测试、真实失败报告和文档不砍。
- **纯 headless 无 GL context**：不额外安装复杂显示栈；保留 compile/link 和真实失败证据，将 runtime 标为 `SKIP` 并列入第 17 周前重验，不声称 runtime 已通过。
- **FFmpeg 可选编码器不可用**：查询实际 encoder 后选择一个已安装编码器并在素材 README 固定；不下载替代素材，不开始编译整套 FFmpeg。
- **Wireshark/dumpcap 无权限**：保留版本和 `-D` 错误，记录最小权限修复建议；不使用 root 进行真实抓包，不让抓包权限阻塞核心编译环境，除非本机岗位环境明确要求。
- **Sanitizer 与特定编译器组合不可用**：先用 Week1 已验证的另一编译器复现并记录组合；不得用普通崩溃冒充 sanitizer 诊断。
- **时间不足**：删除 Qt 探测增强、JSON 总报告、彩色输出和自动安装；保留 P0 smoke、失败路径、资源清理、至少 6 个测试与第 6 天 1 小时缓冲。
