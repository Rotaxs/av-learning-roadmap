# Weekly Learning Roadmap

为指定周生成可执行、可验收的音视频开发学习路线，并直接写入对应周目录。不要只在对话中给出建议。

## 适用范围

在用户表达以下意图时使用：

- “生成第 N 周学习路线”
- “这周应该学什么”
- “创建 WeekN 的详细计划”
- “继续下一周”
- 要求补充或调整某一周的学习内容、项目或验收标准

本 Skill 只负责本仓库中的周学习路线。不要用于修改两年总路线，除非用户明确要求。

## 必须读取的上下文

执行前必须：

1. 读取工作区根目录的 `学习路线.md`，找到指定周所属阶段、阶段目标、任务、交付和“不做”范围。
2. 检查目标周目录是否已经存在。存在时先阅读已有路线和项目规格，不覆盖用户代码或学习记录。
3. 如果不是第一周，检查最近一个已有周目录的路线、项目状态或复盘，用于识别前置知识和欠账；不存在时按根路线生成，不虚构完成情况。
4. 用户没有给出周次且无法从现有目录推断时，只问一个问题：要生成第几周？

根路线是范围和节奏的权威来源。不得擅自把后续阶段的大型任务提前，也不得为了内容丰富增加与本周目标无关的框架、协议或项目。

## 目录规则

目录中的 Phase 按根路线阶段的出现顺序从 1 开始，Week 使用全局周次：

```text
Phase{顺序编号}/
  Week{全局周次}/
    学习路线.md
    project/
      README.md
      src/
      include/
      tests/
    notes/
    evidence/
```

映射规则：根路线“阶段 0”对应 `Phase1`，“阶段 1”对应 `Phase2`，以此类推。示例：第 1 周对应 `Phase1/Week1`；根路线“阶段 1（第 3-12 周）”中的第 3 周对应 `Phase2/Week3`；第 19 周对应 `Phase4/Week19`。生成的周路线必须同时写明根路线阶段名称，避免编号歧义。

执行时创建所需目录。空目录可以暂不创建；一旦产生源码、测试、笔记、日志、截图、抓包或性能报告，必须放入对应 Week 目录：

- `project/`：本周要交付的源码、构建文件、测试和项目说明。
- `notes/`：概念笔记、源码阅读记录、数据流图和问题清单。
- `evidence/`：测试报告、日志、抓包、性能数据和演示说明。

不得把周项目放在仓库根目录，也不得为同一周另建名称不一致的项目目录。如果本周工作是现有核心项目的一部分，在 `project/README.md` 中写清未来合并目标；本周代码仍先保存在本周目录，除非用户已经有核心项目仓库并明确要求直接集成。

## 执行流程

### 1. 确定本周边界

从根路线提取并明确：

- 所属阶段与阶段目标
- 本周主题和交付物
- 上一周提供的前置能力
- 后续一至两周会如何复用本周成果
- 本周明确不做的内容

若根路线将多周合并描述，应结合阶段交付拆出当前周最小闭环，不能把整段任务全部塞入一周。

### 2. 先设计本周总体内容

路线开头先给出简洁的周级概览，让用户在开始前能快速回答“这周学什么、做什么、最后得到什么”。总体部分只包含：

- 所属阶段、本周主题和前后衔接。
- 3-5 个核心知识模块及其学习边界，每个模块用 1-3 句话概括。
- 本周项目的输入、处理链路、输出和 P0 闭环。
- 周末必须达到的能力和最终交付物清单。
- 本周明确不做的内容。

总体部分不要展开阅读步骤、实验步骤、自测题，也不要逐模块重复“学什么、为什么、怎么学、掌握标准”。这些执行细节统一放入具体日期，确保整份路线只有一条按天推进的执行主线。

控制知识范围。核心知识模块都必须服务于本周项目。优先使用官方文档、标准、man page、项目 examples 和源码；不要堆砌课程链接。若提供具体网络链接，应确认链接真实有效。

### 3. 设计本周项目

项目必须是可在一周内完成的最小版本，并与根路线交付一致。项目说明至少包含：

- 背景与训练目的
- 与阶段主项目的关系
- 输入、处理链路和输出
- 功能需求与优先级：P0 必做、P1 时间允许、明确不做
- 建议目录和最小接口；只有接口能帮助理解边界时才提供，不代写完整实现
- 正常、边界、错误和资源释放测试
- 构建与运行方式的预期形式
- 可量化验收标准
- 常见错误、定位工具和排查顺序
- 完成后应保留的证据

不要把“阅读完成”“代码能跑”作为唯一标准。根据本周主题使用可验证指标，例如测试数量、连续运行时间、内存错误、线程退出、输出字节数、时序误差、丢包统计或性能基线。

### 4. 安排一周节奏

默认按 18-22 小时、6 天学习、1 天休息设计。根据任务调整，不机械平均：

- 第 1 天：前置检查、概念和最小实验
- 第 2-3 天：核心知识与项目骨架
- 第 4 天：完成 P0 主链路
- 第 5 天：测试、故障注入和调试
- 第 6 天：修复、文档、验收和复盘

`每日任务` 是周路线的主体，必须按实际执行顺序写，而不是把前文知识模块重新列一遍。每天固定包含：

- **今日目标**：当天结束时应形成的一项明确能力或项目进展。
- **预计时间**：给出总时长；必要时给各任务分配时间，避免任务量失真。
- **学什么**：列出当天涉及的概念、API、数据结构或工具的具体范围，并标注“必须掌握”“必须会用”或“了解即可”。
- **怎么学**：给出阅读顺序、官方资料类型、最小实验、观察点和调试方法。不能只写“学习某概念”或“阅读文档”。
- **动手任务**：列出当天要编写、修改、运行或调试的具体内容，说明正常路径和当天涉及的失败路径。
- **当天交付**：逐项写出当天新建或更新的相对文件路径，以及文件中应包含的内容；没有必要交付文件时明确写“无新增文件”，不能为了凑交付而制造空笔记。
- **自测问题**：提供 2-4 个能口述、计算、编码或调试的问题，用于判断是否理解当天内容。
- **结束条件**：使用可观察、可勾选的结果判断当天是否完成，例如测试数、命令退出结果、输出字节数、日志、截图或性能数据。

知识应在首次需要它的日期中完整讲清，后续日期只引用和应用，不重复长篇解释。每天的文件交付要共同覆盖周级交付清单，不能到路线末尾才首次说明需要保存什么。

总时长必须落在根路线建议范围内；缓冲时间应明确保留，不能排满全部时间。休息日不安排补课或隐含任务。

### 5. 写入文件

创建或更新以下文件：

#### `PhaseN/WeekN/学习路线.md`

固定使用以下结构：

```markdown
# 第 N 周：主题

## 本周概览
### 所属阶段
### 这周学什么
### 本周项目
### 完成标准
### 最终交付物
### 本周不做
## 前置检查
## 每日任务
### 第 1 天：主题（预计 N 小时）
#### 今日目标
#### 学什么
#### 怎么学
#### 动手任务
#### 当天交付
#### 自测问题
#### 结束条件
### 第 2 天：主题（预计 N 小时）
<!-- 第 2-6 天沿用相同结构，第 7 天默认休息 -->
## 周末总验收
## 常见风险与降级方案
## 周末复盘问题
## 与后续路线的衔接
```

`本周概览` 应控制篇幅，只建立全局认知，不写成第二份详细教程。所有学习步骤、实践任务、交付路径和每日验收都写在对应日期中。

`前置检查` 只列开始本周前需要验证的能力、工具和阻塞条件。若检查会产生版本记录、薄弱项或日志，应将实际执行和文件保存安排到第 1 天，避免前置检查变成脱离日程的额外任务。

每日任务不能只有术语列表。“怎么学”“当天交付”“自测问题”和“结束条件”必须具体到用户可以直接照着执行。最终交付物必须能追溯到某一天的“当天交付”，周末总验收只汇总验证，不首次引入新任务。

#### `PhaseN/WeekN/project/README.md`

固定使用以下结构：

```markdown
# 项目名称

## 项目目的
## 使用场景
## 输入与输出
## 处理流程
## 功能需求
### P0 必做
### P1 可选
### 本周不做
## 建议结构
## 核心接口与所有权
## 实现步骤
## 构建与运行
## 测试方案
## 验收标准
## 调试指南
## 交付清单
```

未知的真实构建命令不得伪造为已经可用。项目尚未实现时，应标注为“预期命令”或使用占位符，并说明实现后需要更新。

### 6. 复查

写完后检查：

- 周次、Phase 顺序编号和根路线阶段是否正确映射。
- 开头是否先用简洁概览说明这周学什么、做什么和交付什么。
- 是否删除了独立且冗长的“学习内容”章节，避免与每日任务重复。
- 每天是否都写明今日目标、学什么、怎么学、动手任务、当天交付、自测问题和结束条件。
- 每个最终交付文件是否都在某一天明确写出相对路径、内容要求和产生方式。
- 学习目标是否全部在每日自测、项目或周末总验收中得到验证。
- P0 工作量是否能在 18-22 小时内完成。
- 是否包含失败场景、测试、调试和资源释放。
- 是否明确不做范围和任务超时时的降级方案。
- 是否要求所有本周交付物保存在对应 Week 目录。
- 是否避免重复根路线中的通用说明，而是给出本周具体行动。

## 内容质量要求

- 使用中文，技术名词、API 和命令保留官方英文写法。
- 内容具体、可操作，不写“深入理解”“熟练掌握”等无法验收的空话。
- 总体概览负责建立全局认知，每日任务负责全部执行细节；不要在两处重复同一段知识说明。
- 每天按“学习输入 -> 最小实验 -> 项目应用 -> 证据保存 -> 自测验收”的顺序组织，除非任务本身需要不同顺序。
- “当天交付”必须使用 `project/`、`notes/`、`evidence/` 下的明确相对路径，并说明写入内容，不能只写“完成笔记”或“保存日志”。
- 不假设用户已经完成上一周；用前置检查验证。
- 不为了显得完整而引入过度设计。先保证 P0 闭环，再列 P1。
- 对所有权、线程、时间戳、网络或资源生命周期相关任务，必须加入失败路径和退出清理验收。
- 项目代码由用户学习实现。除非用户明确要求，不直接生成完整答案；可以生成构建骨架、测试接口和有指导性的 TODO。
- 已有用户代码或记录只增量修改，绝不删除、覆盖或重建。

## 完成后的回复

简洁说明：

- 已生成哪一周及所属阶段。
- 创建或更新了哪些文件。
- 本周最重要的学习目标和项目交付是什么。
- 如需 OpenCode 重新加载刚修改的 Skill，仅在 Skill 本身发生变化时提醒重启；日常生成周路线不需要提醒。
