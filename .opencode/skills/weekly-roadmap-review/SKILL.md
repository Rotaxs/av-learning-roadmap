# Weekly Roadmap Review

审查本仓库中已经生成的周学习路线是否符合根路线、工作量是否可行、执行与验收是否完整，并直接修正有明确依据的问题。不要只给审查建议，也不要把路线审查变成学习进度验收。

## 适用范围

仅在用户明确表达以下意图时使用：

- “检查第 N 周学习路线”
- “审查这周计划是否合理/可行”
- “修订、优化或补全 WeekN 路线”
- “检查 AI 生成的路线有没有缺失或安排不当”
- 要求核对周路线与项目规格的一致性

以下情况不要触发：

- 生成一个尚不存在的新周路线：使用 `weekly-learning-roadmap`。
- 检查代码、笔记、证据或判断能否进入下一天/周：使用 `learning-progress-check`。
- 用户只是按路线学习、提问或实现项目。

本 Skill 仅手动触发。不要因为 `weekly-learning-roadmap` 刚生成文件就自动调用，除非用户随后明确要求审查。

## 职责边界

默认只允许新增或修改：

- `PhaseN/WeekN/学习路线.md`
- `PhaseN/WeekN/project/README.md`

不得修改：

- 根目录 `学习路线.md`，除非用户明确要求修改总路线。
- `学习进度.md`、学习者代码、测试实现、笔记、证据和日志。
- 学习者写入的自测答案、复盘回答以及已有 `[x]`/`[ ]` 状态。
- 前一周或后一周文件，除非用户同时明确要求审查那些周。

可以读取上述文件来判断路线是否已经开始、环境是否匹配和前置能力是否真实存在，但不能替学习者完成任务或制造证据。

## 确定目标周

1. 用户指定全局周次时，按根路线映射到对应目录。根路线“阶段 0”对应 `Phase1`，“阶段 1”对应 `Phase2`，依次类推；`WeekN` 始终使用全局周次。
2. 用户说“本周”但未给周次时，浏览 `Phase*/Week*/学习路线.md`，默认选择全局周次最大的已有 Week。
3. 若存在两个同样合理的目标，或用户要求审查的周路线尚不存在，只问一个简短问题，不自行创建新路线。
4. 在完成回复中明确写出目标全局周次、目录 Phase 和根路线阶段名称。

## 必须读取的上下文

审查前必须：

1. 读取根目录 `学习路线.md` 中目标周所属阶段、该周任务、阶段目标、阶段交付、闸门和“不做”范围。
2. 完整读取目标周 `学习路线.md` 与 `project/README.md`；路线缺失时停止并转交 `weekly-learning-roadmap`，只有项目 README 缺失时才按本 Skill 的安全规则补齐。
3. 若不是第一周，读取最近一个已有周的 `学习路线.md`、`学习进度.md` 和项目规格，用于识别真实前置能力、阻塞和欠账。没有进度记录时不得假定上一周已完成。
4. 查看目标周是否已有 `学习进度.md`、代码、笔记或证据，用来判断该周是否已经开始。只判断修订安全性，不验收这些成果。
5. 必要时查看后续一至两周在根路线中的任务，确认本周成果是否确实会被复用，避免提前实现后续阶段内容。
6. 检查目标文件及相关工作区差异。保留用户和其他 agent 的已有改动，不回退、不覆盖不相关内容。

根路线是范围与节奏的上位依据；目标周路线是当前执行契约。审查必须同时保护二者，不能为了“更完整”而扩大范围。

## 审查原则

1. **先判断问题，再修改**：每项修改都必须对应根路线偏差、执行阻塞、时间失真、内容缺失、不可验收、内部矛盾或不安全假设。不要只做措辞润色。
2. **最小正确修订**：优先删减、移动、明确或补齐现有内容；只有缺失内容确实服务 P0 时才新增任务、接口或文件。
3. **P0 闭环优先**：先保证输入、处理链路、输出、正常路径、至少一个关键失败路径和可复核证据，再考虑 P1。
4. **可执行而非百科全书**：每天必须能按顺序照做；概览只建立全局认知，不与每日任务重复。
5. **证据与验收对应**：每个硬目标必须有观察方式、阈值或产物；每个最终交付必须在某一天产生或更新。
6. **不虚构环境与结果**：未知命令、依赖版本、设备能力和构建状态只能写为预期或待验证。不得把 URL、API、命令或 package 名称凭印象写成事实。
7. **保护已执行内容**：路线开始后，修订不能让学习者因事后标准变化而失去已经合理取得的完成结论。

## 审查矩阵

逐项审查并在分析中记录“通过 / 需修订 / 需用户决定”。不要因为章节存在就判为通过，必须检查内容是否有效。

### 1. 周次与范围

- Phase 顺序编号、全局 Week 和根路线阶段名称是否映射正确。
- 本周主题、项目和交付是否直接对应根路线该周任务及阶段目标。
- 是否擅自提前后续阶段的大型任务、框架、协议或平台内容。
- 是否明确本周不做，并能阻止最常见的范围膨胀。
- 前一周提供的能力是否通过前置检查确认，而不是被无条件假定。
- 后续衔接是否真实且只说明复用，不把后续实现塞入本周。

### 2. 学习内容质量

- 是否只有 3-5 个服务本周项目的核心知识模块，并写清学习边界。
- 是否区分“必须掌握”“必须会用”和“了解即可”。
- 是否优先使用官方文档、标准、man page、examples 和源码，而非堆砌课程链接。
- 概念是否在首次需要的日期讲清，后续只应用，避免反复抄写。
- 是否存在术语堆砌、空泛目标或与项目无关的阅读任务。

### 3. 项目可行性

- 项目是否是本周可完成的最小版本，并具有明确输入、处理链路、输出和 P0 闭环。
- P0、P1 和“不做”是否互斥且边界清楚；P1 未暗中成为验收前提。
- 接口和目录是否只为解释边界而存在，是否有过度设计或代写完整答案。
- 所有权、生命周期、线程、时间戳、网络和资源清理要求是否与主题匹配。
- 构建运行方式是否标注“预期”或“已验证”，且不伪造当前可用性。
- 与阶段长期项目的关系是否说明清楚，是否错误地产生新的长期仓库。

### 4. 时间与节奏

- 默认是否为 18-22 小时、6 天学习、1 天完全休息；用户另有时间约束时以明确约束为准。
- 各日时间之和是否正确，是否留出明确缓冲而非排满。
- 单日任务是否能在标注时间内完成，包括安装、阅读、编码、调试、测试和文档成本。
- 是否按“前置与最小实验 -> 骨架 -> P0 主链路 -> 测试故障 -> 收口验收”形成依赖顺序。
- 是否在前几天塞入过多环境安装，或直到第 6 天才首次要求关键测试、证据和 README。
- 任务超时时是否先砍 P1，且不牺牲 P0、失败路径、测试、清理和复盘。

时间评估不能只相加标题中的小时。应估算每个动手任务的真实成本；当 P0 在理想环境下也明显超过总时长时，必须缩小 P0。

### 5. 每日可执行性

第 1-6 天均应包含：

- `今日目标`：当天结束时只有一项主要能力或项目进展。
- `预计时间`：与任务量相符；复杂日期必要时给出子任务预算。
- `学什么`：具体概念、API、数据结构或工具及掌握层级。
- `怎么学`：阅读顺序、资料类型、最小实验、观察点和调试方式。
- `动手任务`：明确要编写、运行、修改或故障注入的内容。
- `当天交付`：明确相对路径、文件内容和产生方式；无文件时诚实写无新增文件。
- `自测问题`：2-4 个可口述、计算、编码或调试的问题，不能直接附答案。
- `结束条件`：可观察、可勾选且能在当天完成。

还要检查每日内部顺序是否为“学习输入 -> 最小实验 -> 项目应用 -> 证据保存 -> 自测验收”，以及当天交付和结束条件是否互相对应。

### 6. 测试、调试与安全

- 是否覆盖与本周主题匹配的正常、边界、错误和资源释放场景。
- 测试数量是否服务覆盖面，而不是机械凑数；阈值是否现实且可重复。
- 是否安排至少一次故障注入及明确排查顺序、工具、关键观察和回归。
- 外部进程、文件、内存、锁、线程、socket、窗口、context 等资源是否有错误路径与退出清理。
- 是否要求危险命令、root、敏感抓包、未知脚本、版权不明素材或不可逆系统变更；若有，必须改成安全验证或人工说明。
- 长稳、性能、弱网或设备测试是否有环境前提、测量方法、指标和降级规则。

### 7. 交付与验收闭环

- `完成标准` 是否量化且覆盖周级能力，不以“阅读完成”“代码能跑”作为唯一标准。
- `最终交付物` 中每个路径是否在某一天的 `当天交付` 首次产生或明确更新。
- 每个核心学习目标是否能在自测、项目测试、证据或周末验收中被验证。
- 周末总验收是否只汇总第 1-6 天已有工作，不首次引入任务。
- 验收命令、文件名、target、阈值和项目 README 是否一致。
- 降级方案是否明确哪些可进入 backlog、哪些仍阻塞本周通过。

### 8. 两份文档一致性

核对 `学习路线.md` 与 `project/README.md` 中的：

- 项目名称、目的、输入输出和处理链路。
- P0、P1、本周不做与未来合并目标。
- 目录、接口、所有权和资源生命周期。
- 构建运行命令及“预期/已验证”状态。
- 测试场景、数量、阈值、失败行为和退出码。
- 交付文件路径、证据和验收标准。

冲突时以根路线和更小的可行 P0 为依据修订两份文档；若目标周已经执行，则同时遵循“已开始周次的修订规则”。

## 问题分级

只使用以下级别：

| 级别 | 定义 | 默认处理 |
| --- | --- | --- |
| 阻塞 | 阶段/周次错误、P0 不闭环、工作量明显不可行、关键依赖顺序错误、验收无法执行、安全风险或两文档关键契约冲突 | 必须修订；若已开始且会改变通过条件，先问用户 |
| 重要 | 缺失败路径、交付不可追溯、每日步骤不具体、量化标准缺失、命令状态不真实或缺必要降级 | 直接做最小修订 |
| 建议 | 不影响 P0 的表达重复、P1 排序、轻微可读性或辅助说明问题 | 仅在修改成本低且不会扩大范围时修订 |

不要创建单独的审查报告文件，除非用户明确要求。问题分级用于指导修改和最终回复，避免仓库累积一次性文档。

## 已开始周次的修订规则

出现以下任一证据，即视为目标周已经开始：

- 存在非空 `学习进度.md`。
- `project/` 中已有学习者实现，而不仅是生成器创建的规格骨架。
- `notes/` 或 `evidence/` 中已有本周实际记录。
- 路线每日结束条件已有勾选或自测答案。

对已开始周次：

1. 不修改学习者的答案和勾选状态。
2. 不降低原有 P0、失败路径、安全边界和阶段闸门来让本周更容易通过。
3. 不给已经执行的日期追加新的硬标准；必要补充优先放入尚未执行日期或周末复盘，并清楚标明来源。
4. 可以修正错字、失效路径、错误命令、相互矛盾且显然无法执行的要求，但要保留原意并在回复说明。
5. 若删除或替换已执行任务、提高或降低通过门槛、改变项目接口/输出契约、要求重做已有成果，必须先用一个简短问题征得用户选择。
6. 若问题涉及安全、数据损坏、敏感信息或危险权限，立即修正或移除危险指令，不等待；在回复中明确说明原因。

如果无法判断某日是否已执行，按已开始处理，不冒险重写。

## 修订流程

### 1. 建立事实基线

提取根路线要求、前置状态、目标周原始 P0、总时间、交付物和执行状态。先识别硬约束，再评价文本质量。

### 2. 完成审查矩阵

逐项找出具体问题及对应位置，判断级别、修改依据和是否触发用户确认。没有问题的项不需要在最终回复逐条列出。

### 3. 决定最小修改

按以下优先级处理：

1. 修正阶段映射、安全风险、根路线偏离和 P0 不闭环。
2. 缩小超时范围，移动依赖顺序，补齐失败路径与清理。
3. 让每日任务、交付和验收形成可追溯闭环。
4. 统一路线与项目 README 的契约。
5. 删除重复、空泛或与本周无关内容。

一次修订不要顺便重写整份路线。原结构和内容可用时只做局部编辑。

### 4. 写入文件

直接增量修改目标 `学习路线.md` 和/或 `project/README.md`。缺少其中一个文件时，根据已有文件与根路线补齐固定结构，但不得创建学习代码、测试答案、笔记或证据。

路线结构应与 `weekly-learning-roadmap` 保持一致：

```text
本周概览 -> 前置检查 -> 每日任务（第 1-6 天） -> 第 7 天休息
-> 周末总验收 -> 风险与降级 -> 复盘 -> 后续衔接
```

项目 README 应包含：

```text
项目目的 -> 使用场景 -> 输入输出 -> 处理流程 -> P0/P1/不做
-> 建议结构 -> 接口与所有权 -> 实现步骤 -> 构建运行
-> 测试 -> 验收 -> 调试 -> 交付清单
```

### 5. 二次复查

修改后必须重新检查：

- 全部时间相加是否落在预算内，缓冲和休息是否真实存在。
- P0 是否在该时间内可完成，P1 是否可直接删除而不破坏闭环。
- 两份文档中的命令、路径、接口、测试数、退出码和阈值是否一致。
- 每个最终交付是否能追溯到具体日期。
- 周末验收是否没有新增工作。
- 是否误改答案、勾选、进度、代码、证据或其他周文件。
- 是否仍有未解决的阻塞问题或需要用户决定的取舍。

必要时运行 Markdown、链接或仓库已有的安全检查；不要执行学习项目、安装依赖或制造验收证据，因为本 Skill 审查的是路线质量而非完成情况。

## 特殊情况

### 路线不存在

停止并说明目标周尚无路线，建议使用 `weekly-learning-roadmap`。不要在审查名义下从零生成整周。

### 项目 README 不存在

若周路线明确要求项目且目标周未开始，可根据路线补齐 README；若已开始，先检查现有项目结构，补充规格时不得否定或重构学习者实现。

### 根路线过于概括

可以拆出服务阶段交付的最小周闭环，但不得将个人偏好当作根路线要求。存在多个同样合理且会显著改变项目方向的方案时，只问一个问题。

### 网络资料或 API 无法确认

优先改写为“查阅对应版本的官方文档/帮助”并安排当天验证，不保留可能虚假的具体链接、API 或命令。只有能确认时才写具体来源。

### 路线合理且完整

不为了显示工作量而修改文件。明确说明未发现需要修订的问题，并指出残余风险，例如实际环境、设备或学习者基础尚未验证。

## 完成后的回复

简洁说明：

- 审查了哪一周、目录 Phase 和根路线阶段。
- 发现的阻塞/重要问题及其影响；无问题时明确说未发现。
- 修改了哪些文件和关键内容。
- 是否因该周已开始而保留了原标准，是否还有需要用户决定的事项。
- 本次修改了 Skill 本身时，提醒用户退出并重启 OpenCode；日常使用本 Skill 修订路线时无需提醒重启。
