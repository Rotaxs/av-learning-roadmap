# Learning Progress Check

检查本仓库每日、每周或阶段学习任务的真实完成情况，以对应周的 `学习路线.md` 为主要标准，以根目录 `学习路线.md` 的最小闭环和阶段闸门为上位标准。默认将结论写入对应 Week 目录的 `学习进度.md`，不要只在对话中给出主观评价。

## 适用范围

在用户表达以下意图时使用：

- “检查今天的学习任务”或“第 N 天完成了吗”
- “检查本周进度”“进行周末验收”或“第 N 周能通过吗”
- “检查这个阶段”“阶段复盘”或“能否进入下一阶段”
- “我能进入下一天/周了吗”
- 要求根据学习成果、代码、日志、笔记或回答判断完成情况
- 要求找出欠账、阻塞、证据缺口或给出改进建议

本 Skill 只检查和记录学习完成情况。生成或重写周学习路线应使用 `weekly-learning-roadmap`；实现学习项目、代答自测题或补造验收证据不属于本 Skill。

## 核心原则

1. **路线定义标准**：周路线中的每日结束条件、周完成标准、最终交付物和周末总验收是主要依据；根路线中的最小学习闭环、阶段交付和闸门用于补充及解决冲突。
2. **证据决定结论**：勾选框和用户声明是待核验信息，不是完成证据。文件存在也不等于内容有效。
3. **执行结果优先**：可以安全复现时，实际构建、测试和运行结果优先于旧日志；无法执行时明确标记“未复验”，不得推断通过。
4. **不替用户过关**：检查时不得修改学习项目代码、测试、笔记、证据或路线勾选项来满足标准。只允许新增或更新对应的 `学习进度.md`；发现问题后报告，不直接修复，除非用户另行明确要求。
5. **P0 优先**：P0 主链路、正常与失败路径、可复现构建、必要测试、调试证据和复盘不可被 P1 成果替代。P1 未完成通常进入 backlog，不阻塞通过。
6. **诚实处理不可自动核验项**：口述、现场操作、设计解释和自测理解需要向用户提问或现场演示。没有回答时标记“待口述验证”，不能判为已完成。
7. **给出最小下一步**：建议只针对真实缺口，默认不超过 3 条，并区分进入下一日/周/阶段前必须完成与可进入 backlog 的事项。

## 确定检查范围

### 用户已指定范围

按用户指定的日期、全局周次或阶段检查。目录中的 Phase 映射遵循：根路线“阶段 0”对应 `Phase1`，“阶段 1”对应 `Phase2`，依次类推；Week 始终使用全局周次。

### 用户未指定范围

依次检查：

1. 浏览现有 `Phase*/Week*/学习路线.md` 和 `学习进度.md`。
2. 选择全局周次最大的已有 Week，除非其进度记录表明应回到更早的阻塞周。
3. 检查该周每日结束条件，选择最早尚未有充分证据完成的学习日作为“今日检查”候选。
4. 在报告中写明推断出的范围和依据。存在两个同样合理的候选时，只问一个简短问题，不擅自选择。

“今天”默认指路线中的当前学习日，不按自然星期机械映射。休息日不转化为补课日。

## 必须读取的上下文

执行任何检查前必须：

1. 读取根目录 `学习路线.md`，找到相关阶段目标、阶段交付、闸门、“不做”范围和通用最小闭环。
2. 读取目标 `PhaseN/WeekN/学习路线.md` 的本周概览、指定日期任务、结束条件、最终交付物、周末总验收和降级方案。
3. 读取 `PhaseN/WeekN/project/README.md`，识别 P0、P1、预期命令、测试方案和项目验收标准。
4. 检查目标 Week 下 `project/`、`notes/`、`evidence/` 和已有 `学习进度.md`。只读取与本次标准有关的内容，不以文件数量评价完成度。
5. 周检查还应查看本周相关 Git diff 和提交历史；阶段检查应读取阶段内每周的最新 `学习进度.md`、周路线和关键交付，不能只汇总百分比。
6. 工作区存在无关或他人改动时忽略，不修改、不回退。若改动直接影响核验，只将其标为“未提交但可检查”或说明冲突。

若目标周还没有周路线，停止验收并说明缺少权威标准；不要依据根路线的一行摘要虚构每日完成标准。可建议先使用 `weekly-learning-roadmap` 生成该周路线。

## 证据层级

按以下优先级判断，低层级证据不能推翻高层级失败：

1. **本次复验**：安全执行的构建、测试、静态/动态检查或项目运行结果及退出码。
2. **可复核产物**：实现代码、测试、配置、报告、抓包、性能数据、调试记录及其内容之间的一致性。
3. **历史记录**：带命令、日期、环境、退出状态和关键输出的日志；Git 提交可证明过程，但不能单独证明行为正确。
4. **学习者回答**：对口述题、数据流、所有权、线程模型、错误定位和技术取舍的回答。
5. **自报与勾选**：只能作为检查线索。

以下不能单独视为完成：

- 只有 `[x]`，但没有路线要求的交付或证据。
- 空文件、模板、TODO、占位内容或 README 中仍标为“预期命令”的命令。
- 只写“测试通过”而没有测试数、命令、退出码或关键输出。
- 日志显示缺少工具、命令失败或结果属于旧实现。
- 只有正常路径，没有路线明确要求的边界或错误路径。
- 代码能跑，但无法从干净目录构建，或学习者不能解释和修改。
- 为满足数量而生成、复制或伪造的低价值证据。

## 状态定义

每个检查项只能使用以下一种状态：

| 状态 | 定义 |
| --- | --- |
| 已完成 | 标准已满足，并有与要求匹配的充分证据 |
| 部分完成 | 已有有效成果，但标准只满足一部分 |
| 待口述验证 | 文件无法证明，必须由学习者回答或现场操作 |
| 证据不足 | 可能做过或已勾选，但证据缺失、过期或不可复核 |
| 阻塞 | 前置能力、环境、工具或主链路故障使任务无法继续 |
| 未开始 | 未发现对应成果或执行记录 |
| 不适用 | 经路线降级规则确认，本次无需完成；必须写明理由 |

总体结论使用：

- **通过**：本次范围内所有硬标准已完成；仅允许存在不阻塞的 P1 backlog。
- **有条件通过**：主链路和安全边界已满足，只剩路线明确允许后移且不影响后续的事项。必须列出条件和期限。
- **未通过**：任一硬标准未满足、关键项证据不足、仍待必要口述验证或存在阻塞。

不得用简单完成百分比决定是否通过。可以显示 `已完成项/总检查项` 作为概览，但必须同时显示硬标准状态。

## 检查流程

### 1. 建立验收矩阵

从路线逐项提取本次范围的标准，并为每项记录：

- 标准原文的简短摘要
- 类型：P0、P1、每日结束条件、周完成标准、最终交付、周末验收或阶段闸门
- 预期证据路径或验证方式
- 是否为硬标准

合并完全重复的标准，但保留更严格的阈值。周路线与项目 README 冲突时，以周路线为准并在报告中指出；周路线低于根路线的阶段闸门时，阶段检查采用根路线标准。

### 2. 静态核验

检查相关文件的实际内容：

- 源码和构建配置是否覆盖要求的主链路及错误处理。
- 测试是否真实覆盖要求场景，而非仅满足数量。
- README 命令、target、路径和当前实现是否一致。
- 日志是否包含命令、环境、关键结果、失败信息和退出状态。
- 调试或性能证据是否包含复现条件、观察、结论和回归。
- 笔记是否回答路线要求的薄弱项、数据流、根因或复盘，而非按篇幅判断。
- Git 记录是否能支持过程结论，且构建产物、敏感信息未被误纳入。

不要要求路线没有规定的文件或格式，也不要因命名风格差异否决等价且清晰的证据。

### 3. 动态复验

仅执行满足以下条件的命令：

- 命令来自已实现项目的准确 README、构建配置或路线验收步骤。
- 不安装软件、不访问凭据、不修改系统配置、不启动长期驻留服务、不删除用户成果。
- 构建产物写入已约定且被忽略的 build 目录；若这会污染工作区或覆盖现有证据，改用新的临时 build 目录。
- 命令能在合理时间内结束。

优先验证 configure/build、自动测试、关键正常样例和至少一个关键错误样例。涉及 Sanitizer、性能、长稳、真实设备、网络故障或人工界面的任务，只有环境允许且成本合理时复验；否则核验已有证据并标记复验限制。

记录实际命令、退出码和关键结果。命令失败后不要修改项目以求通过；收集首个可行动错误并归类为实现失败、环境阻塞或文档失效。

### 4. 口述与现场验证

对路线要求但无法从仓库确认的能力，一次提出 2-4 个高价值问题，优先覆盖：

- 数据或控制流
- 资源所有权、生命周期或线程退出
- 一个失败场景的定位过程
- 一个设计取舍及其代价

问题必须来自本周路线，不额外扩大知识范围。收到回答后根据准确性、独立性和能否联系项目证据判定；回答不完整时指出具体缺口，不用措辞流畅度代替技术正确性。

如果用户只要求先检查文件，可以先生成暂定报告，将相关项标记为“待口述验证”，总体结论必须为“未通过”，直到验证完成。

### 5. 判定放行

#### 进入下一学习日

当天 P0、结束条件和会阻塞次日的交付必须完成。仅独立的笔记润色或明确 P1 可进入 backlog。

#### 进入下一周

本周 P0 闭环、周完成标准、最终交付和周末总验收必须通过；主链路失败、测试/失败路径缺失、关键证据缺失或无法解释时不放行。路线降级方案明确允许后移的环境项可以“有条件通过”，但必须成为下一周首要阻塞。

#### 进入下一阶段

必须汇总该阶段全部周的硬标准，并实际核验阶段交付和根路线闸门。不能因为最后一周通过就忽略早期欠账，也不能因为少量 P1 backlog 阻塞阶段推进。主链路、稳定性、安全退出、可复现性或阶段要求的核心解释能力任一失败时不放行。

### 6. 生成改进建议

根据根因而不是症状给建议，默认最多 3 条，顺序如下：

1. 修复主链路或解除环境/前置阻塞。
2. 补齐失败路径、测试和可复核证据。
3. 补概念、工具使用或复盘；只有全部硬标准已完成时才可推荐一个 P1 强化项。

每条建议必须包含：

- 具体动作和目标文件/命令/能力
- 原因及对应证据缺口
- 预计时间
- 类型：“进入下一日/周/阶段前完成”或“Backlog”

建议应使用路线已有的降级方案。时间不足时优先删除 P1，不得建议降低 P0、删除失败路径或伪造证据。若连续两次检查出现同类问题，建议增加回归测试、固定排查清单或根因复盘；若连续延期，建议减少下一周 P1 或使用根路线缓冲周，而不是叠加欠账。

## `学习进度.md` 写入规则

每日和周检查写入目标 `PhaseN/WeekN/学习进度.md`。阶段检查先用周级结论更新阶段内各 Week 的进度文件，再在该阶段最后一个已有 Week 的 `学习进度.md` 写入独立的“阶段汇总”章节；不要用阶段结论替换某一周的当前结论，也不要在 Phase 根目录另造格式。

## 各粒度的最低输出

### 每日检查

- 覆盖当天所有结束条件和当天交付。
- 指出是否会阻塞下一天。
- 未到周末时不提前宣告整周通过。

### 每周检查

- 汇总每日硬标准，但重点重新核验周完成标准、最终交付和周末总验收。
- 报告 P0、P1、证据和口述验证各自状态。
- 明确“可以进入下一周”“有条件进入”或“暂不进入”。

### 阶段检查

- 列出阶段内每周结论与遗留硬标准。
- 实际核验阶段交付、连续运行/性能/Sanitizer/弱网等阶段指标。
- 对薄弱项做趋势分析，例如反复缺失败测试、日志不可复核、依赖照抄或同类故障重复出现。
- 最终建议聚焦下一阶段必须关注的 1-3 项能力，不重新设计整条路线。

## 边界与安全

- 不根据代码行数、笔记字数、提交次数或学习时长直接判断完成。
- 不要求提交敏感数据、受版权限制的素材或大型构建产物作为证据。
- 不运行来源不明、需要 root、修改网络/系统配置或具有破坏性的脚本。此类任务只核验脚本内容和已有执行证据，并说明限制。
- 不删除失败日志。失败记录可以是有效学习证据，但不能被当作成功证据。
- 不因用户落后而自动降低标准；使用路线允许的降级方案，或建议调整节奏。
- 不因用户提前完成 P1 而跳过当前 P0。
- 检查发现路线本身存在矛盾或不可验收标准时，单独指出并建议修订路线，不擅自改变标准。

## 完成后的回复

简洁说明：

- 检查了哪个日期、周次或阶段，以及总体和放行结论。
- 哪些证据已实际复验，哪些受环境限制或仍需口述。
- 最重要的 1-3 个阻塞或下一步。
- 已更新哪个 `学习进度.md`。

如果本次新建或修改了 Skill 本身，提醒用户退出并重启 OpenCode；日常运行检查只更新学习进度时不需要重启。
